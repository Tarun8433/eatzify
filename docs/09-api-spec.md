# 09 — API Specification

Base: `https://api.eatzify.app/v1` · JSON only · TLS 1.3 · JWT access (15 min) + rotating refresh (30 d)

## 1. Conventions

- Request/response bodies are `snake_case`.
- **No health data in paths or query strings.** Ever. POST a body, even for reads that need filters.
- `Idempotency-Key` header **required** on all POSTs that create money or plans. Server stores the key
  for 24 h and replays the original response.
- Pagination: cursor-based. `?limit=20&cursor=<opaque>` → `{ data: [], next_cursor, has_more }`.
  No offset pagination on any list a user can grow unbounded.
- Every response carries `X-Request-Id`. Every log line carries it. Support tickets quote it.
- Every list endpoint is scoped server-side by the caller's identity. Never accept a `user_id` from a
  client to determine scope.

## 2. Error envelope (single shape, everywhere)

```json
{
  "error": {
    "code": "PLAN_GATE_BLOCKED",
    "message": "A plan can't be generated for this profile.",
    "user_message": "Based on what you've told us, a plan generated by an app isn't the right tool here…",
    "details": { "gate": "ckd", "referral": true },
    "request_id": "01J9…"
  }
}
```

`message` is for developers and logs. `user_message` is the only string the app is allowed to show —
it comes from the approved copy in doc 05 §7, server-side, so a policy change doesn't need an app release.

**Codes:** `AUTH_REQUIRED` `AUTH_EXPIRED` `FORBIDDEN` `NOT_FOUND` `VALIDATION_FAILED`
`AGE_INELIGIBLE` `PLAN_GATE_BLOCKED` `PLAN_GATE_CLINICIAN` `RATE_LIMITED` `ENTITLEMENT_REQUIRED`
`CONSENT_REQUIRED` `CONSENT_EXPIRED` `IDEMPOTENCY_CONFLICT` `PAYMENT_FAILED` `AFA_REQUIRED`
`INSUFFICIENT_FOOD_COVERAGE` `CONFLICT` `SERVER_ERROR`

HTTP: 400 validation · 401 auth · 403 forbidden/entitlement/consent · 404 · 409 conflict/idempotency ·
422 domain rejection (gates, age) · 429 rate limit · 5xx.

## 3. Auth

```
POST /auth/otp/request      { phone_e164 }                      → 204   (rate limit 3/hour/number)
POST /auth/otp/verify       { phone_e164, otp, device }          → { access, refresh, user, onboarding_required }
POST /auth/refresh          { refresh }                          → { access, refresh }   (rotate; reuse ⇒ revoke family)
POST /auth/logout           { refresh }                          → 204
GET  /auth/me                                                    → { user, roles, entitlements, active_plan_summary }
```

DLT-registered templates for OTP SMS via MSG91. Never log an OTP. Never return whether a number exists.

## 4. Profile & plans

```
POST /profile/onboarding    { profile, health_profile, consents[] }
  → 201 { user_id, health_profile_version, gates[] }
  → 422 AGE_INELIGIBLE | PLAN_GATE_BLOCKED

GET  /profile                                → { profile, health_profile, latest_measurements }
PATCH /profile/health                        { …changed fields } → creates a new version, returns it
POST /measurements          { kind, value, unit, recorded_at }
  → 201 { measurement, is_suspect }   (is_suspect true ⇒ app shows confirm dialog)
```

**4.2 Generate a plan**
```
POST /plans/generate
Idempotency-Key: <uuid>
{ "regenerate_reason": "user_request" }        // inputs come from the server-side profile, never the client
→ 201 {
    "plan": { "id","valid_from","valid_to","targets":{…},"meals":[…] },
    "rule_pack_version": "1.0.0",
    "warnings": [ { "code":"safety_clamp_applied", "user_message":"…" } ],
    "trace_available": true
  }
→ 422 { error.code: "PLAN_GATE_BLOCKED", details.gate: "pregnancy" }
→ 429 RATE_LIMITED   (entitlement plan.regenerate_per_day exhausted)
```

```
GET  /plans/active                                  → active plan + revision
GET  /plans/{id}/trace                              → engine trace (coach & admin only; audited)
POST /plans/{id}/override    { meal_id, items[] }    → 201 new revision (coach only, scope plan_edit)
POST /plans/{id}/export      { format: "pdf" }       → 202 { job_id } → async, notify on ready
GET  /plans/{id}/alternates?item_id=…                → alternates within ±10% kcal, ±5g protein
```

Override validation: server re-runs the safety clamps (doc 05 §2) against the overridden totals and
rejects with `VALIDATION_FAILED` + `details.floor_violated` if a coach tries to go below a floor.
The UI must not be the only thing stopping this.

## 5. Food & logging

```
GET  /foods/search?q=dal&limit=20                → published foods only, synonym-aware
GET  /foods/{id}                                  → nutrition + household measures
POST /foods/custom          { name, kcal, macros, measures[] }   → user-scoped custom food
POST /logs/food             { diary_date, slot, food_id|recipe_id|custom, quantity_g|measure }
GET  /logs/day?date=YYYY-MM-DD                    → totals + entries + plan comparison
POST /logs/food/preview     { food_id, measure+measure_count | quantity_g }
                                                  → the portion's kcal, macros, fibre, sodium, added sugar,
                                                    saturated fat — scaled by the same code as the log (D-238)
GET  /foods?group=pulse,egg                        → any-of docs/03 §4 groups; unknown → 400 FOOD_GROUP_INVALID
GET  /foods/scan/status                           → { allowed, reason, tier, daily_limit, remaining_today,
                                                      requires_ad, trial_ends_at }
POST /foods/scan            multipart image (jpeg|png ≤ 5 MB), ad_watched
                                                  → { scan_id, dish_name, confidence, items: [{ name, grams, kcal,
                                                      protein_g, carb_g, fat_g, fibre_g, sodium_mg, added_sugar_g,
                                                      saturated_fat_g }], totals } — an AI ESTIMATE (D-240)
POST /foods/scan/{id}/log   { slot, keep?: [item indexes] } → the entry (estimated: true, image_url = signed photo)
DELETE /foods/scan/{id}                           → the pending photo, deleted now
GET  /logs/food/{id}/photo?exp=&sig=              → the entry's own photo; the signature is the permission
                                                    403 ENTITLEMENT_REQUIRED | AD_REQUIRED · 429 SCAN_LIMIT_REACHED ·
                                                    503 SCAN_UNAVAILABLE · the photo is never stored (D-238) · vendor per FOOD_VISION_PROVIDER (D-239)
PATCH /logs/food/{id}                             → 409 if locked_at is set (48h rule)
POST /logs/water            { diary_date, ml }
POST /logs/steps            { diary_date, steps, provider }
GET  /logs/summary?from=&to=                      → adherence, macro averages, trend (MA7)
```

`GET /logs/day` returns `diary_date` resolved by the server using the 04:00 IST boundary. The client
must not compute it independently — one implementation, server-side, exposed to the app.

## 5a. Gym (ADR-013)

Every route is the signed-in person's own training, JWT-guarded, free on every tier (D-245). The
server resolves diary days, progression, records and energy; the app renders them.

```
GET    /gym                            → settings, week, routines, today, week_days (server-resolved),
                                         session_plans (every routine's next session, prefilled and
                                         progressed — a workout can start offline), totals
                                         { today_kcal, week_kcal, streak_weeks, … }, recent
GET    /gym/exercises                  → library (1,324, D-244) + the person's own; no steps
GET    /gym/exercises/{id}             → exercise with en/hi steps, best, last session, best e1RM,
                                         plan_entry (what adding it now would start with), routine_ids
GET    /gym/exercises/{id}/progress    → points (top set | e1RM | effort), last 5 sessions, best
POST   /gym/exercises                  { name, body_part, description? }   → 409 GYM_EXERCISE_EXISTS
PATCH  /gym/exercises/{id}             own exercises only → 403 GYM_NOT_OWNER
DELETE /gym/exercises/{id}             leaves routines; past workouts keep the name stamped on them
POST   /gym/routines                   { name, icon, progression, exercises[] }
PUT    /gym/routines/{id}              saved whole; supersets = adjacent exercises sharing an id
DELETE /gym/routines/{id}              also cleared from the week and any one-off day
POST   /gym/routines/starter           → push / pull / legs, Mon / Wed / Fri (empty days only)
PUT    /gym/schedule                   { week: { "1": routine_id | null, … "7": … } }
POST   /gym/schedule/day               { date, routine_id? , rest? }  → one date only
PATCH  /gym/settings                   { rest_sec, effort_scale, keep_awake, sound, body_figure }
POST   /gym/workouts                   { id (uuid, made by the phone), routine_id?, name, started_at,
                                         ended_at, body_weight_kg?, entries[] }
                                       → idempotent on id; server computes volume, PRs, e1RM records,
                                         working weights, diary_date, energy_kcal (D-242) + energy_basis
GET    /gym/workouts?before=&limit=    → cursor paging, newest first
GET    /gym/workouts/{id} · DELETE /gym/workouts/{id}
GET    /gym/calendar?month=YYYY-MM     → 6 Monday-first weeks: trained / planned / changed, summary
GET    /gym/stats?muscle_window=week|30d|90d|all&effort_window=30d|90d|1y|all&hard=true
                                       → tiles, 53-week heatmap, muscle levels (+ untrained, neutral),
                                         effort (RIR/RPE), 30 days of workout energy, recent, exercises
```

`energy_kcal` is `(MET − 1) × kg × hours`, MET from `energy_reference` rows (Compendium codes). It is
also returned on `GET /logs/day` as `activity.workout_kcal` — its own figure, never added to
`energy_burned_kcal` and never subtracted from the day's target (D-242). Null means "not estimated".
Errors: `GYM_INVALID` (422), `GYM_EXERCISE_NOT_FOUND` / `GYM_ROUTINE_NOT_FOUND` / `GYM_WORKOUT_NOT_FOUND`
(404), `GYM_EXERCISE_EXISTS` (409), `GYM_NOT_OWNER` (403).

## 9. Admin

Every admin endpoint requires role `admin`/`super_admin` **and** writes an `audit_log` row when the
response contains a health field or PII.

```
POST /admin/users/search      { query, filters }             (POST: filters may include conditions)
GET  /admin/users/{id}                                       → audited read
POST /admin/foods             { …food }                      → draft
POST /admin/foods/{id}/review → reviewed   POST …/publish → published
POST /admin/foods/import      { csv }                        → async, per-row validation report
POST /admin/coaches/{id}/verify { verified_attributes }
GET  /admin/tickets           POST /admin/tickets/{id}/reply
POST /admin/notifications     { title, body, segment }        → segment.condition allowed only when
                                                                content_class = "clinical" (doc 13 §5)
GET  /admin/metrics/overview                                 → excludes is_demo
GET  /admin/audit?actor=&subject=&from=&to=
POST /admin/rule-packs/activate { version }                  → super_admin only, requires reviewed_by
GET  /admin/scan-policy                                      → per-tier scan rules (D-238)
PATCH /admin/scan-policy/{tier} { enabled, daily_limit, requires_ad, trial_days } → X-TOTP required
```

There is deliberately **no** `GET /admin/users/export.csv` for non-super-admin roles, and the
super-admin version requires a stated reason that lands in the audit log. Your current admin screen
has an unrestricted "Export CSV" button next to a list showing full emails and phone numbers.

## 10. Rate limits

| Endpoint class | Limit |
|---|---|
| `auth/otp/request` | 3/hour/number, 10/day/IP |
| `plans/generate` | entitlement-driven (FREE 1/day, BASIC 2/day, PRO 3/day) |
| `foods/search` | 60/min/user |
| write endpoints | 120/min/user |
| admin | 300/min/user |
| webhooks | unlimited, but signature-verified and idempotent |

## 11. Versioning & deprecation

URL-versioned (`/v1`). Additive changes only within a version. Breaking change ⇒ `/v2` with both live
for 90 days minimum. Clients send `X-App-Version`; the server can return
`{ "upgrade_required": true }` in a wrapper for a hard minimum-version gate — you will need this the
first time a safety rule changes.
